# IoT 平台数据可靠性说明

## 当前数据路径

```
设备 → Gateway(MQTT/HTTP/CoAP) → Yate extmodule → iotdev → 数据库
```

请求是**同步链路**：收到一条就写一条库，写成功才返回。能否“保证数据可靠”取决于你在哪一段能接受故障窗口。

---

## 不需要 Kafka 也能做到的可靠性

在以下条件下，**不引入 Kafka 也能满足多数场景**：

| 措施 | 说明 |
|------|------|
| **使用可持久化的数据库** | 用 **MySQL 或 PostgreSQL**，并开启持久化（如 MySQL `innodb_flush_log_at_trx_commit=1`、PostgreSQL 默认 WAL），掉电/重启后已提交的数据不丢。 |
| **设备侧重试** | MQTT 使用 **QoS 1**（至少一次）；HTTP/CoAP 失败时设备或上层做重试。这样“网络闪断/网关短暂不可用”不会丢数据（可能重复，可去重）。 |
| **避免 SQLite 做生产库** | SQLite 无多进程强一致、无复制，故障时更容易丢或坏库，仅适合单机开发/测试。 |

在这种配置下：**数据一旦在 DB 里提交就是可靠的**；唯一的风险是“已到网关/Yate 但还没落库”时进程或机器挂了，会丢这一小段。

---

## 何时考虑引入 Kafka（或其它消息队列）

在以下需求下，引入 **Kafka**（或 RabbitMQ、Pulsar 等）更有价值：

| 需求 | 说明 |
|------|------|
| **进程/节点故障零丢数** | 希望 Gateway 或 Yate 宕机、重启时，已收到但尚未写库的数据**一条都不丢**，只延迟写入。 |
| **写入与入库解耦** | 接入层只负责把数据写入队列，入库由独立消费者异步完成，便于削峰、限流、独立扩容。 |
| **回溯与重放** | 需要按 offset 重新消费、补算、审计或重导入历史数据。 |
| **多消费者** | 同一份数据既要入库，又要进实时计算/告警/数仓等，多路消费同一流。 |

引入后的典型形态：

```
设备 → Gateway → Kafka（持久化日志）→ 消费者 → Yate/DB 或直写 DB
```

- 数据先落 Kafka，再被消费者写入当前库（或直写 DB），Gateway/Yate 重启只影响延迟，不影响“是否写入”。
- 若消费者直写 DB，可不再经 Yate，需自行实现鉴权与写库逻辑（或保留一个轻量服务调 Yate 的 iot.uplink）。

---

## 建议归纳

| 场景 | 建议 |
|------|------|
| 一般物联网、监控、日志类 | **不必须引入 Kafka**。用 MySQL/PostgreSQL + 设备重试 + 可选去重即可。 |
| 计费、审计、合规要求“不能丢一条” | 引入 **Kafka（或同类队列）**，Gateway 先写 Kafka，再异步入库。 |
| 接入量极大、需要削峰与多路消费 | 引入 **Kafka** 做缓冲与多消费者。 |

**结论**：**不是“要保证数据可靠就必须上 Kafka”**。先做好 DB 持久化 + 设备/协议层重试，多数场景已经够用；只有在需要“进程级零丢数、解耦、回溯或多路消费”时，再引入 Kafka 更合适。
